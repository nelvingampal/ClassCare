## Remaining release blockers and limits

- Run the new and existing rule suites before deploying any Firestore rule changes. Unit mocks do not compile/execute Firestore rules.
- Rerun registration/approval, concerns/replies, enrollment, attendance, deep check, summative scores, revoked access, exports and offline reconnect with real synthetic Auth/Firestore. Existing browser suite covers a subset; it is not complete system certification.
- Existing on-device PII retention in concern history/offline queues remains outside this repair. No production records were inspected or scrubbed, including any previously stored initial_password fields.
- Manual enrollment is still a series of Auth/profile/counter/request writes. Failures after account creation can leave partial state; a trusted transactional provisioning service or reconciliation workflow remains necessary for robust production operation.
- Teacher support actions use an admin-only audit_log path and DB.logAudit currently catches denial; this pre-existing workflow needs a deliberate append-only staff audit policy and end-to-end verification. Do not claim support notes are durably saved merely from the current success toast.
- Production App Check enforcement, hosting headers, credentials/integrations and deployed indexes/rules are unverified. No outbound delivery was attempted.
- Frontend password removal prevents new plaintext writes but is not a migration of existing records. Default credentials already handed out would need partner-managed resets.

## Reproduce on an environment permitting local sockets and Edge

Use Java 21, the locked Node dependencies and installed Microsoft Edge. No production project selection is needed.

```powershell
npm test
npm run test:rules
npm run emulators
```

Keep emulators running. In another terminal, run the suites sequentially because they reset the same synthetic database:

```powershell
npm run test:browser
node tests/integration.cjs
node tests/reliability.cjs
npm run test:accessibility
```

Startup follow-up: use `Start-ClassCare.cmd` or `npm start` from the normal Windows terminal to start and await Auth/Firestore plus the web server. The launcher creates only admin@demo.classcare.test, teacher@demo.classcare.test and student@demo.classcare.test, password ClassCareDemo123!, with student scanner ID DEMO-001. These are synthetic identities; live credentials do not work in the emulator. Runtime verification remains BLOCKED here by loopback EACCES. The old web-only process was stopped after the user reported failure. `npm run start:web` serves only static pages and does not start Firebase. Stop the launcher before running the suites above to avoid competing fixture resets and ports.

Implementation references: [Firebase field validation](https://firebase.google.com/docs/firestore/security/rules-fields), [WAI modal focus pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/). These references describe the approach, not evidence that this application passed a security or accessibility certification.

After the blocked runtime checks pass, the authorized local commit can be created from a terminal with repository write access using `git add` on the files listed in the current diff and `git commit -m "Repair local startup, registration, record access and scanner accessibility"`. Review the staged diff first; deployment and push remain separate.
